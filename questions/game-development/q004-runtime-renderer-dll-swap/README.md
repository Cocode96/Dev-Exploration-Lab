# Q004, 런타임 렌더러 DLL 교체 구조 비교

원본 Discussion: [DX9, DX11, DX12 렌더러를 DLL로 분리하면 실행 중 교체할 수 있을까?](https://github.com/Cocode96/Daily-Dev-Questions/discussions/4)

## 질문

DX11과 DX12처럼 여러 렌더러 백엔드를 제공할 때 다음 두 구조 중 어떤 방식을 선택해야 하는가?

1. 백엔드마다 별도 DLL을 제공하고 실행 중 DLL을 교체한다.
2. 하나의 DLL을 유지하고 DLL 내부에서 백엔드를 전환한다.

비교 기준은 런타임 전환 비용, 리소스 재생성 비용, 배포와 유지보수다.

## 처음 예상

단일 DLL 내부 전환은 이미 로드된 모듈을 유지하므로 실행 중 전환 비용이 작을 것으로 예상했다. 분리 DLL은 모듈 언로드, 로드, 함수 주소 조회가 추가되지만 백엔드별 독립적인 배포와 교체에는 유리할 것으로 예상했다.

## 검증 방법

Python Experiment Runner로 `renderer_compare.exe`의 두 구조를 반복 실행했다.

- Release 빌드
- 구조별 준비 실행 3회
- 구조별 본 측정 30회
- A/B 실행 순서를 고정 seed로 혼합
- 성공 횟수, 중앙값, P95, 최솟값, 최댓값 기록

실행 도구와 설정은 [`experiments/python/benchmark-runner`](../../../experiments/python/benchmark-runner)에 있다. 원본 측정값은 [`raw_results.csv`](../../../experiments/python/benchmark-runner/reports/q004-dll-architecture-comparison/raw_results.csv)에 보존했다.

별도의 실제 렌더러 구현에서는 텍스처를 바인딩하고 백엔드 전환 시 리소스를 다시 만드는 흐름까지 최소한으로 확인했다. 다만 아래 30회 수치는 DLL 구조 자체를 비교한 마이크로벤치마크다.

## 측정 결과

| 구조 | 성공 | 전환 중앙값 | P95 | 최솟값 | 최댓값 |
|---|---:|---:|---:|---:|---:|
| 분리 DLL | 30/30 | 955.05us | 1,186.70us | 881.40us | 1,260.40us |
| 단일 DLL 내부 전환 | 30/30 | 3.50us | 9.30us | 3.20us | 22.90us |

이번 마이크로벤치마크에서 분리 DLL 전환 중앙값은 단일 DLL 내부 전환보다 약 273배 컸다. 두 분포도 겹치지 않았다. 분리 DLL의 최솟값 881.40us는 단일 DLL의 최댓값 22.90us보다 컸다.

DLL 파일 크기 합계는 분리 구조가 28,672바이트, 단일 DLL이 15,360바이트였다.

## 결과 해석

분리 DLL 구조는 전환할 때 기존 모듈을 내리고 새 모듈을 로드한 뒤 필요한 함수 주소를 다시 얻는다. 단일 DLL 구조는 이미 로드된 모듈 안에서 구현만 선택하므로 DLL 관리 경로가 짧다.

다만 이번 수치를 실제 게임의 렌더러 전환 시간으로 그대로 적용할 수는 없다. 실제 게임에서는 다음 비용이 추가될 수 있다.

- GPU 작업 완료와 Fence 대기
- 디바이스와 스왑체인 재생성
- 대형 텍스처와 버퍼 재업로드
- 많은 descriptor와 파이프라인 상태 재생성
- 콜백, 스레드, COM 객체 수명 정리

실제 렌더러 실험에서 리소스 바인딩과 재생성을 최소한으로 확인했지만 작은 테스트 리소스를 사용했다. 재생성 비용이 큰 리소스를 사용하는 게임에서는 전환 시간이 이번 관찰보다 훨씬 커질 수 있다.

## 확인된 결론

실행 중 렌더러나 백엔드를 자주 교체해야 한다면 단일 DLL 내부 전환이 적합하다. 모듈을 반복해서 로드하고 내리지 않으므로 전환 비용이 작고 런타임 수명 관리 지점도 줄어든다.

반대로 프로그램 시작 시 백엔드를 한 번 선택하고 이후에는 교체하지 않는 구조라면 약 1ms 수준의 초기 선택 비용은 중요하지 않을 수 있다. 이 경우에는 백엔드별 독립성, 선택적 배포, 교체와 유지보수를 위해 분리 DLL로 제공하는 편이 더 좋을 수 있다.

따라서 어느 구조가 항상 우수한 것은 아니다.

> 자주 교체한다면 단일 DLL 내부 전환을 사용하고, 시작할 때 한 번 선택한다면 성능보다 배포와 유지보수를 기준으로 분리 DLL을 고려한다.

최종 선택 전에는 실제 프로젝트의 리소스 수와 크기로 다시 측정해야 한다.

## 실험의 한계

- 30회 측정값은 DLL 구조 마이크로벤치마크다.
- 실제 렌더러의 대규모 GPU 리소스와 스트리밍 환경을 재현하지 않았다.
- 한 PC의 캐시, 보안 프로그램, 드라이버 상태에 영향을 받을 수 있다.
- `process_ms`는 한 프로세스에서 두 구조를 모두 실행하므로 구조 비교 지표로 사용하지 않았다.
