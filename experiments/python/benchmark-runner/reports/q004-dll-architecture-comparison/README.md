# Q004 DLL architecture microbenchmark

## 질문

실행 중 렌더러 백엔드를 바꿀 때 다음 두 구조의 DLL 관리 비용은 얼마나 다른가?

1. 백엔드마다 별도 DLL을 사용하고 전환 시 DLL을 교체한다.
2. 하나의 DLL을 유지하고 DLL 내부에서 백엔드를 전환한다.

## 실험 조건

- 실행 파일: `renderer_compare.exe`
- 빌드: Release
- 준비 실행: 구조별 3회
- 본 측정: 구조별 30회
- 실행 순서: 고정 seed로 무작위 혼합
- 통계: 중앙값, P95, 최솟값, 최댓값
- 원본 데이터: [`raw_results.csv`](raw_results.csv)

## 결과

| 구조 | 성공 | 전환 중앙값 | 전환 P95 | 전환 최솟값 | 전환 최댓값 |
|---|---:|---:|---:|---:|---:|
| 분리 DLL | 30/30 | 955.05us | 1,186.70us | 881.40us | 1,260.40us |
| 단일 DLL 내부 전환 | 30/30 | 3.50us | 9.30us | 3.20us | 22.90us |

이 실험에서는 분리 DLL 전환 중앙값이 단일 DLL 내부 전환보다 약 273배 컸다. 두 분포도 겹치지 않았다. 분리 DLL의 최솟값 881.40us는 단일 DLL의 최댓값 22.90us보다 컸다.

DLL 파일 크기 합계는 분리 구조가 28,672바이트, 단일 DLL이 15,360바이트였다.

## 해석

분리 DLL 구조는 전환 과정에서 모듈 언로드, 새 모듈 로드, 함수 주소 조회 같은 작업을 수행한다. 단일 DLL 구조는 이미 로드된 모듈 안에서 구현만 선택하므로 DLL 관리 경로가 더 짧다.

따라서 실행 중 백엔드를 자주 전환하는 기능에서는 단일 DLL 내부 전환이 DLL 관리 비용 측면에서 유리하다. 프로그램 시작 시 백엔드를 한 번만 선택한다면 약 1ms 수준의 차이는 전체 시작 비용에 비해 중요하지 않을 수 있다. 독립 배포, 플러그인 교체, 선택적 의존성 격리가 목적이라면 성능 비용을 감수하고 분리 DLL을 선택할 수 있다.

## 제한사항

이 결과는 DLL 구조 마이크로벤치마크다. 실제 DX11 또는 DX12 디바이스, 스왑체인, GPU Fence, 텍스처 리소스를 생성하지 않는다. 따라서 이 결과를 실제 DX11/DX12 렌더러 전환 성능이라고 표현할 수 없다.

또한 `renderer_compare.exe`는 한 프로세스에서 분리 구조와 단일 구조를 모두 측정한다. Python 어댑터는 각 실행에서 해당 구조의 출력만 선택한다. 보고서의 `process_ms`는 두 구조의 작업을 모두 포함하므로 구조 비교 지표로 사용하지 않는다.

실제 DirectX 자동 벤치마크도 소규모로 시도했지만 렌더러 DLL 로딩 시 Windows 오류 225가 발생했다. Windows는 이 오류를 바이러스 또는 잠재적으로 원치 않는 소프트웨어로 인해 작업을 완료하지 못한 상태로 설명한다. 실제 DX 초기화가 시작되지 않았으므로 유효한 DX 측정값은 생성하지 않았다.

## 현재 결론

> DLL 로딩과 언로딩을 포함한 모듈 교체 비용은 이미 로드된 단일 DLL 내부 전환보다 유의미하게 크다. 하지만 실제 DX11/DX12 렌더러 교체에서는 GPU 동기화와 리소스 재생성 비용이 추가되므로 현재 배율을 그대로 적용할 수 없다.

실제 렌더러에 대한 최종 결론을 내려면 보안 차단 원인을 해결한 뒤 다음 항목을 같은 조건으로 측정해야 한다.

- 디바이스와 스왑체인 재생성 시간
- GPU idle과 Fence 대기 시간
- 텍스처 개수별 리소스 재생성 시간
- 반복 전환 실패율과 메모리 증가량
- Debug Layer 오류와 Device Removed 발생 여부
- 전환 중 최대 프레임 정지 시간
